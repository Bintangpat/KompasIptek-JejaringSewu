## 1. Alasan Pengembangan
> **Catatan Penting:** Bagian ini HARUS SINGKAT (maksimal 2–3 kalimat langsung pada inti masalah/kebutuhan bisnis).

Memperbaiki kegagalan validasi `ERR_VALIDATION_FAILED` pada `POST /api/v1/auth/otp/send` akibat tidak dikirimkannya field wajib `purpose` dari frontend Web. Selain itu, menyelaraskan alur login utama form Web agar melakukan autentikasi kredensial kata sandi nyata ke `POST /api/v1/auth/login` (alih-alih keliru memanggil OTP tanpa token sesi), menghapus field non-whitelisted `deviceId` pada `otp/verify`, serta memperbaiki *envelope unwrapping* pada Axios interceptor.

## 2. Pengembangan Fitur & Mekanisme Teknis

### 2.1 Penyelarasan Tipe Data Autentikasi (`Web/src/features/auth/types.ts`)
- **Tujuan Teknis:** Menjamin kepatuhan skema data klien terhadap DTO NestJS (`SendOtpDto` dan `VerifyOtpDto`) untuk mencegah penolakan oleh `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true`).
- **Mekanisme & Alur Kerja:**
  - Menambahkan tipe serikat (`union type`) `OtpPurpose = "REGISTRATION" | "FORGOT_PASSWORD" | "VERIFY_ACTION"`.
  - Memperbarui antarmuka `OtpSendPayload` dengan menambahkan properti wajib `purpose: OtpPurpose`.
  - Menghapus properti `deviceId` dari `OtpVerifyPayload` karena backend `VerifyOtpDto` secara ketat hanya menerima `identifier` dan `otpCode`.
  - Mendefinisikan `OtpResponseResult` (`{ success?: boolean; message: string }`) untuk merefleksikan respons aktual dari endpoint OTP backend.
- **Berkas Terkait:**
  - [`Web/src/features/auth/types.ts`](file:///D:/Projects/KompasIptek/Web/src/features/auth/types.ts): Penyesuaian antarmuka DTO klien.

### 2.2 Penyesuaian API Client & Mutasi Auth (`Web/src/features/auth/api.ts` & `hooks.ts`)
- **Tujuan Teknis:** Memperbaiki fungsi API dan React hooks mutasi agar mengonsumsi tipe payload baru dan menangani nilai balik sesuai kontrak API.
- **Mekanisme & Alur Kerja:**
  - `authApi.sendOtp`: Mengirimkan payload `{ identifier, purpose }` dan mengembalikan `Promise<OtpResponseResult>`.
  - `authApi.verifyOtp`: Mengirimkan payload `{ identifier, otpCode }` dan mengembalikan `Promise<OtpResponseResult>`.
  - `useAuthActions`: Mengupdate `sendOtpMutation` dan `verifyOtpMutation` dengan generic tipe `OtpResponseResult`, serta menampilkan pesan sukses toast yang relevan.
- **Berkas Terkait:**

  - [`Web/src/features/auth/hooks.ts`](file:///D:/Projects/KompasIptek/Web/src/features/auth/hooks.ts): Pustaka mutasi autentikasi reaktif.

### 2.3 Perbaikan Interceptor Envelope Unwrapping (`Web/src/lib/api-client.ts`)
- **Tujuan Teknis:** Memastikan pemanggil fungsi API memperoleh data payload bersih dari standard JSON envelope `{ success: true, data: T, timestamp, path }`.
- **Mekanisme & Alur Kerja:**
  - Pada interceptor respons Axios, kondisi `if (response.data && response.data.data !== undefined)` kini mengembalikan `response.data.data` (sebelumnya mengembalikan `response.data`), sehingga properti seperti `data.accessToken` dan `data.user` dapat langsung diakses oleh pemanggil tanpa perlu *double unwrap*.
- **Berkas Terkait:**
  - [`Web/src/lib/api-client.ts`](file:///D:/Projects/KompasIptek/Web/src/lib/api-client.ts): Interceptor respons Axios klien.

### 2.4 Konteks Autentikasi Global (`Web/src/context/auth-context.tsx`)
- **Tujuan Teknis:** Menyediakan penanganan galat transparan pada `login()`, default purpose yang valid pada `sendOtp()`, dan payload bersih pada `verifyOtpLogin()`.
- **Mekanisme & Alur Kerja:**
  - `sendOtp`: Menambahkan parameter opsional `purpose` dengan default `"VERIFY_ACTION"`.
  - `verifyOtpLogin`: Menghapus pengiriman `deviceId: "web-client-01"` yang sebelumnya memicu penolakan validasi ketat backend.
  - `login`: Menghapus *swallowing error* (`return { success: true, message: "Mode demo aktif" }`) dan menggantinya dengan melempar ulang `throw err` agar komponen UI (`LoginPage`) dapat menampilkan pesan galat spesifik dari backend kepada pengguna.
- **Berkas Terkait:**
  - [`Web/src/context/auth-context.tsx`](file:///D:/Projects/KompasIptek/Web/src/context/auth-context.tsx): Provider state auth reaktif.

- **Tujuan Teknis:** Menghadirkan alur masuk kredensial password nyata ke sistem backend NestJS dengan pengalaman pengguna yang tangguh dan informatif.
- **Mekanisme & Alur Kerja:**
  - **Autentikasi Utama Berbasis Kata Sandi:** Form submit menjalankan `handlePasswordLogin` yang memanggil `login({ identifier, password })` ke endpoint `POST /api/v1/auth/login`. Jika berhasil, sesi JWT disimpan dan pengguna diarahkan ke dashboard sesuai role (`ADMIN_BUMDES`, `ADMIN_BAPPERIDA`, `SUPER_ADMIN`, `WARGA`).

  - **Verifikasi OTP:** Di dalam modal dialog, penekanan "Verifikasi & Masuk" memanggil `verifyOtp({ identifier, otpCode })` dengan penanganan loading spinner dan feedback toast.
  - **Controlled Inputs:** Menghubungkan input tab Email ke state `identifier` secara controlled dua arah (`value={identifier}`, `onChange`).
  - **Akun Contoh Terverifikasi:** Menginisialisasi default state dengan akun terdaftar di seed database (Admin BUMDes Pagelaran: `081234567891` / `AdminBumdes123!`).

## 5. Keamanan & Integritas Transaksi (Financial & Security Integrity)
- **Anti-Mass Assignment:** Menghilangkan pengiriman properti asing (`deviceId` pada `VerifyOtpDto`) yang berpotensi memicu celah injeksi atau penolakan transaksi.
- **Zero-Trust Tokenization:** Token akses JWT tetap disimpan di in-memory state dan refresh token tersimpan di HttpOnly Cookie `jejaring_pringsewu` untuk perlindungan dari pencurian token via serangan XSS.
- **State Integrity:** Role dan identitas pengguna yang berhasil login langsung diambil dari entitas User terotentikasi di database.

---

## 6. Penanganan Galat & Edge Cases (Failure Modes & Resilience)
- **Missing Purpose Handling:** Parameter `purpose` diproteksi secara statis dengan TypeScript union type dan secara runtime dengan default fallback `"VERIFY_ACTION"`.
- **Offline / Server Down Graceful Fallback:** Jika backend tidak dapat dihubungi saat pengiriman OTP di mode demo, modal verifikasi tetap dapat dibuka dengan peringatan toast informatif.
- **Input Validation UI:** Melakukan pemeriksaan kelengkapan `identifier` dan `password` di sisi klien sebelum request jaringan dikirimkan.
